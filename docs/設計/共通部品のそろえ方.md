# 共通部品のそろえ方

## 決めたこと（2026-11-18）

ヘッダー・フッターなどの共通部品は、**ビルドの仕組みを入れず、`scripts/pages.js` で全ページを同じ形にそろえる**。フレームワーク（Astro など）は、いまは入れない。

- 部品の形は `scripts/pages.js` の `themeNav`（ヘッダーのテーマ切り替えメニュー）と `GITHUB`（フッターのソースコードへの案内）に1つだけ書く
- `node scripts/pages.js` で、`site/` の全ページのその部分を書き換える。`npm test` が食い違いを見つける
- `site/` は「書く場所」と「配る場所」を兼ねたまま。データを作るスクリプト・テスト・`vercel.json`・CSP の検査は何も変えない

## 理由

- ユーザーに届くものは、Astro でもいまの手書きでも同じ静的な HTML なので、速さは変わらない
- Astro を入れると、ビルドと版の管理が増え、テストもビルドが前提になる。インラインの script・style を出す機能（CSP とぶつかる）を使わないよう、人が守り続ける必要もある
- いまの困りごと（同じ部品のコピーを全ページで直す）は、`pages.js` を広げるだけで片付く

## Astro に移るのを考え直すとき

部品が増えて、ページごとの条件分岐が多くなったら考え直す。そのときに気をつけること（レビューで出た点）：

- `publicDir: './site'` にして `site/` は動かさない。テストは書き出した `dist/` を読み、HTML の件数も確かめる（空振りして通るのを防ぐ）
- `build.format: 'preserve'`・`trailingSlash: 'never'`・`build.inlineStylesheets: 'never'`・`compressHTML: false`・`devToolbar.enabled: false`
- 既存の JS は `<script is:inline src="...">` で読み、`.astro` の `<style>`・`client:*`・View Transitions は使わない
- `@astrojs/vercel` は入れない。転送は `vercel.json` に残す
- `scripts/refs.js`（refs.html の目印のあいだを書き換える）も置き換えが要る
- いま目印にしている部品（`<details class="theme-menu">`、フッターの GitHub の行）が、そのまま部品の境目になる
