# 利用者のご意見を集めて使うデータベースの設計

2026-11-15 の案。2026-11-17 に段階1（`supabase/schema.sql` の feedback と、/feedback のフォーム）を書いた。SQL は Supabase に反映済みで、/feedback のフォームは動いている（`site/js/feedback.js` の `LIVE` は true）。決めてよい点は末尾の「決めること」。

## 目的
利用者から、陳情の内容・文面を直すのに役立つ情報（誤り・足りない根拠・言い回し・議会ごとの手続きの違い・よくある質問）を受け取り、運営者（あなた）が**見落とさず、短い時間で選別し、直した記録まで残せる**ようにする。

## いま使えるもの
- Supabase の `council_tips`：議会の手続きの情報だけを受け取る。anon は書き込みだけで読めない。運営者は Supabase の管理画面で見る（`supabase/schema.sql`、`site/js/report.js`）。
- 同じ接続元からの連続投稿は、`report_guard` にハッシュだけ残して制限している（IP は残さない）。
- 足りないもの：文面・理由・根拠への指摘を受ける口、状態の管理（直した／根拠待ち）、どの項目に指摘が集まっているかの集計、直した記録との結びつき。

## 受け取る口（入口）
| 入口 | 中身 | 入れ方 |
|---|---|---|
| サイトのフォーム（新設） | 各テーマの作成画面・項目ごとに「この文面へのご意見」 | 利用者が直接書き込む（`council_tips` と同じ方式） |
| 有料質問（mond など。規約を読んでから） | 陳情書の書き方・出し方の質問 | 運営者が、質問の趣旨を**自分の言葉で要約して**手で入れる（質問の原文は、規約を確かめるまで写さない） |
| 応援のときのメッセージ（BMC など） | 感想・要望 | 運営者が手で入れる。掲載の同意とは別に扱う |
| メール・X | 指摘・質問 | 運営者が手で入れる |

## テーブル `feedback`（案）
氏名・住所・連絡先の列は作らない（`council_tips` と同じ方針）。連絡が要る指摘は、運営者が相手の連絡手段で返し、記録には残さない。

```sql
create table public.feedback (
  id bigint generated always as identity primary key,
  created_at timestamptz not null default now(),
  channel text not null check (channel in ('site','paid_q','gift_msg','mail','x')),
  kind text not null check (kind in ('fact_error','missing_source','wording','missing_item','council_procedure','question','other')),
  theme text check (theme in ('kodomo','dansei','nihonjin','shiho','kenko','sonota')),
  target text check (char_length(target) <= 100),      -- 項目の id（asks-*.js の id）や議会名
  body text not null check (char_length(body) between 5 and 1000),
  source_url text check (char_length(source_url) <= 300 and source_url ~ '^https?://'),  -- 利用者が示した根拠
  -- ここから下は運営者だけが書く（anon の insert では入れられない）
  status text not null default 'new' check (status in ('new','needs_source','accepted','declined','duplicate','done')),
  merged_into bigint references public.feedback(id),
  primary_checked boolean not null default false,     -- 一次資料で確かめたか
  owner_note text,                                     -- 運営者のメモ（非公開）
  resolution_url text,                                 -- 直したコミット・PR の URL
  faq boolean not null default false,                  -- よくある質問の候補
  updated_at timestamptz not null default now()
);
```
- 書き込みの制限は `check_tip` と同じ作り（接続元ごとのハッシュで1日の件数を制限。`report_guard` を `fb:` 付きで使う）。`status` などの運営者の列は、トリガーで入力値を無視して初期値にする。
- anon は insert だけ（`channel` は `site` に固定、書ける列は `kind, theme, target, body, source_url` だけ）。読めない。
- 本文に氏名・住所・電話番号が書かれていたら、運営者が `body` から消す。フォームに「個人が特定できる情報は書かないでください」と書く。

## 運営者が見やすくする（ここがいちばん大事）
Supabase の画面だけだと、どの項目に何件来ているかが見えず、直した記録もつながらない。次の3つを用意する。
1. **ビュー**（Supabase の管理画面で開くだけで使える）
   - `feedback_inbox`：status が `new` のものを、古い順に。
   - `feedback_by_target`：theme・target ごとの件数と最新日。**指摘が集まっている項目**が上に来る。
   - `feedback_faq`：`faq = true` のもの。
2. **手元で使う道具** `scripts/feedback.js`（案）
   - `node scripts/feedback.js pull`：新しい指摘を取り込み、`docs/調査/ご意見/YYYY-MM-DD.md` に、テーマ・項目ごとにまとめて書き出す（いまの `docs/調査/` の使い方と同じで、読んで判断できる）。項目の id から、該当する文面と参考資料の場所も書き添える。
   - `node scripts/feedback.js mark <id> <status> [--url <PR の URL>]`：状態を変える。
   - 鍵（service_role）は環境変数だけに置き、Git に入れない。
3. **直すときの手順**（CLAUDE.md のきまりに沿う）
   - 指摘に根拠の URL があれば、その原文まで当たる。報道・解説だけのものは文面に使わない。
   - 一次資料で確かめられたら `primary_checked = true`、文面を直して `status = done` と PR の URL。確かめられなければ `needs_source` とし、当たれなかった履歴を [一次資料に当たれていない資料](../調査/一次資料に当たれていない資料.md) に残す。
   - 同じ内容は `duplicate` にして `merged_into` で結ぶ。

## よくある質問と有料質問の使い方
- 質問（`kind = question`）のうち、何人にも当てはまるものを `faq = true` にし、答えを一次資料つきで書いて FAQ のページに載せる。答えが一度できれば、有料質問のほうは「FAQ をご覧ください」と短く返せる。
- 有料質問の質問者は匿名が前提。質問の原文は写さず、要約だけを入れる。法律相談に当たらない範囲（一般的な出し方の案内だけ）に答える方針は、[応援の受け付けのTODO](../非公開/応援と運営費/応援の受け付けのTODO.md) の確認が済んでから。

## 守ること
- **応援・有料質問をした人の意見を優先しない。** 取り込みの順番も採否も同じ基準（一次資料で確かめられるか）で決める。サイトの「応援しても陳情の内容は変わりません」という約束を守るため、`feedback` に支払いの有無の列は作らない。
- 個人情報の扱い（個人情報保護法のうえで、氏名等を持たない記録に当たるか、プライバシーポリシーのページが要るか）は、**まだ法令の原文で確かめていない**。確かめるまでは、個人が特定できる情報を受け取らない・残さない作りにする。
- 保存期間：`done`・`declined` になって1年たったものは消す、でよいか決める。

1. `feedback` の SQL（テーブル・トリガー・ビュー）を `supabase/schema.sql` に足す。サイトに「この文面へのご意見」のフォームを置く。

3. FAQ ページと、`feedback_by_target` を見て直す運用。
4. 有料質問の入口（規約を読んでから）。
